## 1. Incremental Alembic migrations (`5b7db4b`)
- The old `0001_initial` was `Base.metadata.create_all` — incompatible with incremental migrations (a later ALTER would clash on a fresh DB). Replaced it with an **autogenerated explicit baseline** `8326c9605659_initial_schema.py` (all 12 tables incl. the 3a/3e/4a columns + the composite `lessons (user_id, day)` PK).
- Removed `Base.metadata.create_all` from the app startup so **Alembic is the single schema authority** (the Dockerfile already runs `alembic upgrade head`). Future changes → `alembic revision --autogenerate` → applied **in place** to existing DBs, no data loss.
- `migrations/README.md` documents the workflow + "don't reintroduce create_all."
- Verified: fresh volume → `alembic upgrade head` builds the schema (`alembic_version` = `8326c9605659`); register/card-add 200. api 126 tests still green (tests build their own SQLite schema directly, unaffected).

## 2. Broad i18n coverage (`c4fcf58`, builds on `032f52b`)
